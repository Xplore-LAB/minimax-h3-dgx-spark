# 故障排查

## 1. `torch.cuda.is_available() = False`

检查：

```bash
docker info
nvidia-container-cli info
docker compose config
```

重新运行：

```bash
make rebuild
make gpu-check
```

不要在容器中执行：

```bash
pip install torch
```

这可能覆盖 NGC 为 ARM64 + GB10 提供的 CUDA PyTorch。

---

## 2. `no kernel image is available for execution on the device`

GB10 计算能力为 SM121。常见原因：

- 使用了不支持 SM121 的旧 PyTorch/CUDA 镜像；
- 第三方 wheel 只编译了 x86 或较旧 GPU 架构；
- 自定义节点覆盖了 torch、triton 或 CUDA 扩展。

处理：

1. 移除最近新增的第三方节点；
2. 恢复默认 `BASE_IMAGE`；
3. 执行 `make rebuild`；
4. 执行 `make gpu-check`。

---

## 3. 容器退出码 137、系统卡顿或 SSH 中断

通常表示统一内存压力过高或系统 OOM。

立即处理：

```bash
make stop
docker ps
free -h
```

修改 `.env`：

```dotenv
RESERVE_VRAM_GB=16
VRAM_HEADROOM_GB=4
ASYNC_OFFLOAD_STREAMS=1
COMFYUI_EXTRA_ARGS=--fast-disk --disable-smart-memory
```

然后：

```bash
make restart
```

工作流同时调整：

- 分辨率下降一档；
- 时长先降至 4 秒；
- Batch 固定为 1；
- 停止其他推理和训练容器；
- 不开启高分辨率预览缓存。

仅在故障诊断且理解影响时，可清理 Linux 文件缓存：

```bash
sudo sync
echo 3 | sudo tee /proc/sys/vm/drop_caches
```

这不是日常提速命令，也不能替代降低任务规模。

---

## 4. `nvidia-smi` 不显示显存总量或显存列为 N/A

DGX Spark 是统一内存架构。部分传统离散 GPU 显存指标在 GB10 上不可用或不能准确反映可供 GPU 使用的物理内存。

重点观察：

```bash
free -h
docker stats --no-stream
dmesg -T | grep -Ei 'oom|killed process'
```

不要只依据 `nvidia-smi` 的显存列判断是否有内存余量。

---

## 5. ComfyUI 中找不到模型

确认路径：

```bash
make verify-models
```

应分别位于：

```text
models/diffusion_models/
models/text_encoders/
models/vae/
```

检查 Compose 实际挂载：

```bash
docker compose config
docker inspect minimax-h3-comfyui --format '{{json .Mounts}}' | jq
```

## 6. Hugging Face 下载失败

先填写 `.env`：

```dotenv
HF_TOKEN=hf_xxxxxxxxx
```

再次运行：

```bash
make download
```

检查磁盘：

```bash
df -hT "$H3_DATA_ROOT"
du -sh "$H3_DATA_ROOT/hf-cache"
```

不要使用多个并发下载进程写同一个目标文件。

---

## 7. 画面全黑、输出损坏或没有音频

确认使用官方匹配组合：

```text
FL2VA INT8 convrot
Qwen3-VL-32B NVFP4 AWQ
Video VAE FP16
Audio VAE FP32
```

不要统一强制所有组件为 FP16/BF16。音频 VAE 应保持官方 FP32 文件。

先恢复官方 Template Library 工作流，关闭第三方节点和自定义采样参数，再做 608×352、4 秒测试。

检查输出文件：

```bash
ffprobe -hide_banner "$H3_DATA_ROOT/output/<文件名>.mp4"
```

## 9. 首次启动长时间停在加载阶段

首次启动会初始化 CUDA、扫描模型目录并加载前端。查看：

```bash
make logs
```

若日志仍持续更新，不要反复重启。若出现明确 Traceback，执行：

```bash
make diagnostics
```

## 10. SageAttention 是否现在安装

基线阶段不安装。

原因：

- GB10 为 SM121；
- 通用预编译 wheel 未必包含 SM121；
- 源码编译会引入 CUDA、编译器和 torch ABI 变量；
- 一旦失败，很难区分是 H3、ComfyUI 还是注意力扩展问题。

先完成官方量化基线。随后单独复制环境或建立新镜像层测试，并保留无 SageAttention 的可回滚镜像。

## 11. 容器重建后崩溃：`ModuleNotFoundError: torchaudio` / ABI 不匹配

**事故**：容器重建（`docker compose up -d` 或 `docker run` 换新实例）后 ComfyUI 启动即崩，
日志报 `No module named 'torchaudio'`（或 `OSError: Could not load libtorchaudio.so`）。

**根因**（两条叠加）：

1. **可写层不持久**：`pip install torchaudio` 直接装进运行中容器的可写层，容器一删就丢。
   ComfyUI 的 H3 音频 VAE（`comfy/ldm/lightricks/vae/audio_vae.py`）import torchaudio，缺失即崩溃。
2. **NGC torch 是定制版，PyPI wheel 装不上**：本机 torch 为
   `2.10.0a0+b558c986e8.nv25.11`（NGC 25.11 定制，commit b558c986e8）。
   PyPI 的 torchaudio 2.10.0 / 2.11.0 / nightly 轮子均为 ABI 不匹配，
   报 `undefined symbol: torch_get_mutable_data_ptr`——**绝对不要用 pip 强装 wheel 覆盖**。

**修复**（已验证通过）：

1. 用匹配 NGC torch 时点的 torchaudio 源码编译（v2.10.0 release 源码要求 stable API 头文件，
   NGC torch 缺 `torch/csrc/stable/`，改用 2025-09-13 的 commit `87ff22e49ed0` 源码成功）：

   ```bash
   # 主机下载源码（codeload 可达，GitHub 直连会 TLS 断）
   curl -L -o /tmp/torchaudio-src.tar.gz \
     https://codeload.github.com/pytorch/audio/tar.gz/87ff22e49ed0
   # 容器内编译（NGC 镜像自带 gcc/cmake/ninja/libsndfile）
   cd /tmp && tar xzf torchaudio-src.tar.gz
   pip install --no-build-isolation --no-deps /tmp/audio-87ff22e49ed0
   python -c "import torchaudio; print(torchaudio.__version__)"   # → 2.8.0a0
   ```

2. **固化进镜像**（关键一步，否则重建又丢）：

   ```bash
   docker commit minimax-h3-comfyui local/minimax-h3-comfyui:v0.30.0-ta
   ```

3. 用新镜像 + 原入口启动（注意 commit 会把临时容器的 `sleep infinity` 入口也固化，
   启动时须显式覆盖回原入口）：

   ```bash
   docker run -d --name minimax-h3-comfyui --gpus all --ipc host --shm-size 16gb \
     --restart unless-stopped -p 127.0.0.1:8188:8188 \
     -e HF_ENDPOINT=https://hf-mirror.com -e H3_DATA_ROOT=/mnt/minimax-h3 \
     -v /mnt/minimax-h3/models:/opt/ComfyUI/models \
     -v /mnt/minimax-h3/input:/opt/ComfyUI/input \
     -v /mnt/minimax-h3/output:/opt/ComfyUI/output \
     -v /mnt/minimax-h3/temp:/opt/ComfyUI/temp \
     -v /mnt/minimax-h3/user:/opt/ComfyUI/user \
     -v /mnt/minimax-h3/custom_nodes:/opt/ComfyUI/custom_nodes \
     -v /mnt/minimax-h3/hf-cache:/data/hf-cache \
     --entrypoint /usr/bin/tini local/minimax-h3-comfyui:v0.30.0-ta \
     -- /usr/local/bin/h3-entrypoint
   ```

**教训**：

- 容器内任何 `pip install` / 文件改动，**要么 commit 进镜像，要么挂载卷**——可写层是临时的。
- NGC torch 是定制版，所有扩展（torchaudio/torchvision 等）必须**源码编译匹配 ABI**，不要装 PyPI wheel。
- `docker commit` 会连入口命令一起固化，重建时检查 `docker inspect <img> --format '{{.Config.Entrypoint}}'`。

**验收**：`curl http://127.0.0.1:8188/system_stats` 返回 200；`docker exec ... python -c "import torchaudio"` 通过；
三档阶梯（608×352 / 736×416 / 864×480）连续生成成功。

## 12. 生成视频默认带声音（用户偏好，2026-08-04 钉死）

**用户要求**：所有 H3 视频生成默认带原生音效，不要静音版。

**原因**：H3 是音画联合模型，但音频需要显式接解码节点才输出。
早期 workflow 只接了视频解码（VAEDecode），没接音频解码（VAEDecodeAudio），
导致噜噜/噜妹/鲸鱼等视频全部无声。

**标准 workflow 音频三件套**（必须全部接上）：

```json
"audio_vae_loader": {"class_type": "VAELoader", "inputs": {"vae_name": "minimax_h3_audio_vae_fp32.safetensors"}},
"audio_decode": {"class_type": "VAEDecodeAudio", "inputs": {"samples": ["sampler", 0], "vae": ["audio_vae_loader", 0]}},
"audio_save": {"class_type": "SaveAudio", "inputs": {"audio": ["audio_decode", 0], "filename_prefix": "audio/h3_xxx"}}
```

**音频 VAE 用官方 FP32 文件**（`minimax_h3_audio_vae_fp32.safetensors`），不要降精度。
音频输出后需用 ffmpeg 与视频 mux 合成带声 MP4。

**要点**：
- 提示词里写清音效描述（如"柴火噼啪声和夜晚虫鸣"），模型会生成对应音效
- 视频 VAE（fp16）与音频 VAE（fp32）是两个不同文件，别混用
- SaveAudio 默认存到 output/audio/ 子目录

## 13. H3 生成的视频有音轨但几乎听不到（音量极低）

**现象**：视频有音轨（ffprobe 能看到 aac/flac），但人耳几乎听不见声音。

**根因**：H3 音频 VAE 解码出的音效电平极低——实测峰值约 **-34 dB**、RMS 约 **-50 dB**
（正常听感峰值应在 -3~-6 dB）。"轻微噼啪声"类提示词会被模型理解成超轻声。
不是微信传输问题，文件本身音轨完好。

**验证方法**：

```bash
ffmpeg -i out.flac -af astats=metadata=1 -f null - 2>&1 | grep -E "Peak level dB|RMS level dB"
# 峰值 < -20 dB 即视为音量过低
```

**修复**（loudnorm 动态响度归一化，推荐）：

```bash
ffmpeg -y -i video_with_audio.mp4 \
  -af "loudnorm=I=-16:TP=-1.5:LRA=11" \
  -c:v copy -c:a aac out_loud.mp4
# 归一化后峰值约 -3.4 dB，RMS 约 -20 dB
```

**经验**：
- 生成后**一律跑 loudnorm**，不要跳过；这是 H3 音频的标准后处理步骤
- 提示词里写音效时可用 "clear and audible ..." 强调音量，但最稳的还是 loudnorm
